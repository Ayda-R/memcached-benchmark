# Memcached Analysis

## Overview

This project investigates behavior on a multicore system using Memcached. The goal is to generate and analyze:

- HITM (Hit Modified) events
- WSS (Working Set Size) behavior

using different CPU affinity configurations and workloads.

## Requirements

- Ubuntu 22.04
- Memcached
- perf
- taskset
- memtier_benchmark
- lstopo

## System Topology

![System Topology](images/lstopo.png)

This figure illustrates the hardware topology of the testing environment generated by the lstopo utility. The system consists of a single NUMA node with approximately 8GB of total memory. The processor architecture exhibits a hybrid design (Performance and Efficient cores):

- **P-Cores (Performance)**: Cores L#0 and L#1 are hyper-threaded, providing two logical processing units each (PU L#0 to L#3). Each P-Core has a dedicated 1.25MB (1280KB) L2 cache, a 48KB L1 data cache, and a 32KB L1 instruction cache.
    
- **E-Cores (Efficient)**: Cores L#2 to L#9 are single-threaded (PU L#4 to L#11). They are organized into two clusters of four cores. Each cluster shares a 2MB (2048KB) L2 cache. Each E-core has a 32KB L1 data cache and a 64KB L1 instruction cache.
Shared Cache: All cores share a unified 12MB L3 cache.

Understanding this asymmetric cache hierarchy is crucial for our Working Set Size (WSS) and False Sharing analysis, as thread placement can significantly impact cache latency and hit rates.

## HITM Experiment

Cache Coherence and HITM Analysis: Single-Core vs. Multi-Core Execution

To quantify the impact of cache line sharing and validate the presence of lock contention/sharing issues in memcached, two distinct scenarios were executed using memtier_benchmark and profiled via perf stat.

- **Base Scenario (Isolated)**: The memcached process was pinned to a single logical core (taskset -c 1). This isolates the process, practically eliminating inter-core cache coherence overhead.
    
- **HITM Experiment (Shared LLC)**: The process was pinned to two logical cores (taskset -c 1,3). Based on the system’s hardware topology, PU L#1 and PU L#3 reside on different physical Performance Cores (P-Cores). They possess independent L1 and L2 caches and only share the 12MB Last Level Cache (L3). A highly contentious workload was generated by restricting the dataset to only 10 keys (--key-maximum=10), forcing threads to repeatedly access and modify the same memory addresses.

### Base Scenario

Run Memcached on only one core:

```bash

MEMCACHED_CORES="1"
CLIENT_CORES="6"
PORT="11211"
```

Results and Analysis:

The performance counters collected over a 4040-second interval reveal a massive throughput collapse caused by cache coherence overhead:

- **Snoop Interventions (HITM)**: The most critical indicator of cache thrashing is the mem_load_l3_hit_retired.xsnp_hitm counter (Hit In Modified). In the isolated Base Scenario, this value was negligible (58,803). However, in the dual-core setup, it exploded to over 19 million (19,094,737). This indicates that cores 1 and 3 are constantly requesting cache lines that have been modified by the other core, forcing costly L3 cross-snoops and invalidations.

- **Cache Activity & CPU Cycles** : As a direct result of this bouncing cache line phenomenon (True/False sharing), total cache references nearly doubled from ~34.5 million to ~66.1 million. Consequently, the CPU had to spend significantly more cycles (8.1 billion vs. 6.6 billion) to execute roughly the same number of instructions, demonstrating severe pipeline stalls due to memory access latency.

This experiment conclusively proves that the lock contention and False Sharing previously identified via perf c2c drastically degrade performance when threads are scheduled across cores that do not share lower-level caches.

Performance Analysis Report: Memory Loads & Network Overhead

Objective:

To analyze the memory load profiling data generated by perf record during the memcached benchmarking session to identify system bottlenecks.

Methodology:

Profiling was conducted using the Linux perf tool, specifically targeting the cpu_core/mem-loads-aux/ event to sample memory read operations on the Performance Cores (P-Cores). The benchmark was executed using memtier_benchmark.

Observations:

The perf report output (based on approx. 24K samples) reveals a significant skew in processing overhead toward the Linux kernel’s network stack rather than the memcached application logic.

- **Kernel Network Overhead**: The top functions contributing to memory load overhead are exclusively kernel-space TCP/IP routing and socket management functions. Notably, tcp_wfree accounts for 20.48%, followed by __ip_local_out (17.13%) and ip_send_check (10.49%).
    
- **Application Logic**: User-space memcached functions represent a minor fraction of the sampled events. Functions such as complete_nread_ascii and item_remove account for only 2.41% and 1.51% respectively.
    Synchronization Primitives: Minor overhead is observed in locking mechanisms, such as native_queued_spin_lock_slowpath (0.54%) and pthread_mutex_lock (0.50%).

Analysis & Conclusion:

The overwhelming dominance of network stack operations indicates a severe loopback bottleneck. Because both the load generator (memtier_benchmark) and the target server (memcached) are likely running on the same host (localhost), the CPU is spending the majority of its time processing high-throughput local network packets rather than executing database operations.

While False Sharing and Cache contention (HITM) are underlying architectural issues within memcached, their visibility in general memory load profiling is currently obscured by this localhost network overhead.

Performance Analysis Report: Cache-2-Cache (c2c) Contention & False Sharing

Objective:

To analyze the perf c2c (Cache-to-Cache) profiling results to pinpoint the exact memory addresses and source code lines responsible for the high HITM (Hit In Modified) rates observed in the memcached benchmark.

Methodology:

The perf c2c tool was used to track shared data cache line contention. We examined the “Shared Data Cache Line Table” and drilled down into the most heavily contended cache line. The offsets within this cache line were mapped directly to the memcached source code using DWARF debug symbols.

Observations:

- Top Contended Cache Line: The perf c2c summary table identifies cache line $0x5ef6379a5600$ as the primary bottleneck, recording the highest number of HITMs (Hit In Modified).
    
- Offset Analysis (The Smoking Gun): Inspecting the details of cache line $0x5ef6379a5600$ reveals two distinct memory offsets being accessed concurrently by different functions:

- Offset $0x28$: Accessed by the get_cas_id function at items.c:106. The source code shows this is a write/increment operation on a shared counter (++cas_id;).
    
- Offset $0x38$: Accessed by the assoc_find function at assoc.c:75. The source code shows this is a read operation checking hash table expansion states (likely reading expand_bucket or hashpower).

- Proximity: The distance between these two variables in memory is only $16$ bytes ($0x38 - 0x28 = 0x10$).

Analysis & Conclusion:

This is a textbook example of False Sharing. A standard CPU cache line is $64$ bytes. Because the heavily written cas_id variable (offset $0x28$) and the heavily read hash table state variables (offset $0x38$) are packed into the same $64$-byte cache line, they share the same cache coherency state.

Every time a CPU core allocates a new item and increments cas_id, it modifies the cache line, forcing the CPU to invalidate this line across all other cores. When another core attempts to simply read the hash table state via assoc_find, it suffers a costly LLC (Last Level Cache) miss and a HITM penalty, as it must fetch the dirtied cache line from the modifying core.

Methodology:

We scaled the number of items ($150$ for L1, $7,000$ for L2, $55,000$ for LLC) to force the working set to fit into specific cache levels. We executed $100,000$ GET requests across these scenarios and measured hardware events using perf stat.

Title: Profiling L1 Data Cache Load Misses in Memcached

Objective:

To identify the user-space functions in memcached that contribute most significantly to Level 1 Data Cache (L1-dcache) load misses, aiming to pinpoint memory access bottlenecks.

**Methodology**:

The profiling was conducted using the perf record command targeting the L1-dcache-load-misses hardware event, filtered specifically for the user-space execution of the memcached binary.

**Key Findings**:

The perf report highlights the following functions as the primary sources of L1 cache misses:

- do_cache_alloc (8.24%8.24%): This function handles memory allocation from the slab allocator. The high miss rate is expected, as allocating memory involves updating internal slab structures (e.g., free lists) which may not reside in the L1 cache.
    
- drive_machine (7.35%7.35%): As the core state machine for handling client connections, this function frequently accesses and updates connection contexts and state variables, leading to scattered memory accesses.
    
- resp_allocate (3.22%3.22%): Similar to do_cache_alloc, allocating structures for client responses involves memory management overhead and cache evictions.
    
- assoc_find (2.33%2.33%) & do_item_get (2.06%2.06%): These functions traverse the hash table and linked lists to retrieve items. Pointer chasing through linked lists is a classic cause of data cache misses because the memory locations are often non-contiguous.
MurmurHash3_x86_32 (1.80%1.80%): Reading key buffers to compute the hash value also contributes to L1 misses, depending on the key size and memory alignment.

**Conclusion**:

The L1 data cache misses in memcached are primarily driven by memory management operations (slab allocation) and connection state tracking. Pointer chasing during hash table lookups (assoc_find) also plays a notable role. Optimizations targeting data locality in the slab allocator and connection state structures would yield the most significant reduction in L1 misses.

Title: Profiling Level 2 (L2) Cache Request Misses in Memcached

**Objective**:

To identify the user-space functions in memcached responsible for Level 2 Cache (L2) misses, specifically focusing on demand request misses (cpu_core/l2_rqsts.miss/upp), in order to understand memory access behaviors that bypass the L2 cache.

**Methodology**:

The system was profiled using perf record with the hardware event cpu_core/l2_rqsts.miss/upp. The output was then filtered for the memcached shared object using perf report --dsos=memcached to isolate the application’s user-space execution overhead.

**Key Findings**:

Unlike the L1 cache profile which was dominated by memory allocation (do_cache_alloc), the L2 cache misses are primarily concentrated around data retrieval, hash table traversal, and protocol parsing:

- item_get (2.81% Children / 0.96% Self): The core function for fetching items from the cache. High L2 misses here indicate that the actual item data objects are frequently not present in the L1/L2 caches, requiring fetches from the Last Level Cache (LLC) or Main Memory.
    
- assoc_find (2.33% Self): The hash table lookup function. Traversing the linked lists within the hash table buckets causes L2 misses due to pointer chasing across non-contiguous memory blocks.
    
- process_bin_get_or_touch (1.85%) & try_read_command_binary (1.06%1.06%): Binary protocol parsing functions. Processing incoming requests requires reading command buffers that may have been evicted from the L2 cache.
    
- mc-lrumaint thread functions (lru_maintainer_thread 0.67%, slabs_available_chunks 0.67%, do_item_link_q 0.41%): Background threads responsible for maintaining the LRU (Least Recently Used) queues. Scanning and unlinking items across large memory spaces naturally incurs L2 misses as the working set size of the LRU queues easily exceeds L2 capacity.

**Conclusion**:

The profile indicates that the Working Set Size (WSS) of the active cache items and hash table structures exceeds the L2 cache capacity. The bottleneck shifts from memory management (seen in L1) to the actual data retrieval logic (item_get, assoc_find) and background LRU maintenance, confirming that random memory accesses during item lookups are the primary drivers of L2 latency.

Title: Profiling Last Level Cache (LLC) Load Misses in Memcached

**Objective**:

To identify the user-space functions in memcached responsible for Last Level Cache (LLC) misses using the cpu_core/LLC-load-misses/upp event. An LLC miss is the most expensive cache penalty, forcing the CPU to fetch data directly from main memory (RAM).

**Methodology**:

The system was profiled using perf record targeting LLC load misses. The results were filtered for the memcached executable (--dsos=memcached) to isolate the application’s direct impact on memory latency.

**Key Findings**:

The profile reveals a stark contrast to L1 and L2 cache behaviors, with a single function overwhelmingly dominating the LLC misses:

- assoc_find (59.01% Children / 58.83% Self): This function is responsible for hash table lookups. Its massive share of LLC misses indicates that navigating the hash table’s buckets and collision chains (linked lists) is the primary cause of main memory fetches. When the Working Set Size (WSS) greatly exceeds the L3 cache, the random memory access patterns (pointer chasing) inherent in linked lists guarantee cache misses at all levels.
    
- memcmp@plt (13.78% Children / 4.44% Self): This is the memory comparison function used extensively by assoc_find to compare the requested key against the keys stored in the hash table chain. The high “Children” overhead confirms it is called sequentially during the lookup process, triggering further memory fetches to read the actual string data of the keys.
    
- Other Functions (e.g., do_store_item, do_item_get): All other functions account for less than 1% of the LLC misses each, proving that the actual fetching or storing of data is negligible compared to the cost of locating the data.

Conclusion:

For large datasets where the WSS exceeds the Last Level Cache, memcached becomes completely memory-bound (Latency Bound) by hash table lookups. The pointer chasing mechanism in assoc_find prevents hardware prefetchers from guessing the next memory address, resulting in severe LLC misses and forcing the CPU to stall while waiting for main RAM.
