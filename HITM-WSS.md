# Memcached Multicore Performance Analysis

An in-depth investigation into multicore system behavior using **Memcached**. This project maps, measures, and analyzes critical hardware interaction metrics under diverse CPU affinity configurations and workloads.

---

## Project Focus

The primary objective of this project is to generate, capture, and analyze two critical hardware-level behaviors:

*   **HITM (Hit Modified) Events:** Pinpointing cache-coherency bottlenecks and dirty cache line transfers.
*   **WSS (Working Set Size) Behavior:** Mapping out memory footprint patterns and cache efficiency characteristics.

---

## Prerequisites & Requirements

Ensure your environment meets the following requirements before running the tests:

*   **OS:** Ubuntu 22.04 LTS
*   **Services:** `memcached`
*   **Profiling Tools:** `perf`
*   **System Utilities:** `taskset` (for CPU pinning)
*   **Benchmark Tool:** `memtier_benchmark`

### Architecture Breakdown

The test system runs on a single **NUMA node** with approximately **8 GB** of total RAM. It features a modern hybrid architecture consisting of Performance and Efficient cores:

#### P-Cores (Performance Cores)
*   **Cores:** Core `L#0` and `L#1`
*   **Threading:** Hyper-threaded, providing 4 logical processing units (`PU L#0` to `PU L#3`)
*   **Cache Design:** 
    *   Dedicated $1.25 \text{ MB}$ ($1280 \text{ KB}$) L2 cache per core
    *   $48 \text{ KB}$ L1 Data cache
    *   $32 \text{ KB}$ L1 Instruction cache

#### ⚙️ E-Cores (Efficient Cores)
*   **Cores:** Core `L#2` to `L#9`
*   **Threading:** Single-threaded (`PU L#4` to `PU L#11`)
*   **Cluster Design:** Organized into two clusters of 4 cores. Each cluster shares a $2 \text{ MB}$ ($2048 \text{ KB}$) L2 cache.
*   **Cache Design:** $32 \text{ KB}$ L1 Data cache and $64 \text{ KB}$ L1 Instruction cache per core.

#### Shared Cache
*   **L3 Cache:** All cores (both P-Cores and E-Cores) share a unified $12 \text{ MB}$ L3 cache.

> [!NOTE]  
> Understanding this asymmetric cache hierarchy is crucial. Thread placement (e.g., pinning threads to E-core shared L2 clusters vs. P-core dedicated L2 caches) directly dictates cache latency, HITM rates, and Working Set Size behavior.


## HITM Experiment

### Cache Coherence & HITM Analysis: Single-Core vs. Multi-Core Execution

To quantify the impact of cache line sharing and validate the presence of lock contention/sharing issues in Memcached, two distinct scenarios were executed using `memtier_benchmark` and profiled via `perf stat`.

*   **Base Scenario (Isolated):** The `memcached` process was pinned to a single logical core (`taskset -c 1`). This isolates the process, practically eliminating inter-core cache coherence overhead.
*   **HITM Experiment (Shared LLC):** The process was pinned to two logical cores (`taskset -c 1,3`). Based on the system’s hardware topology, `PU L#1` and `PU L#3` reside on different physical Performance Cores (P-Cores). They possess independent L1 and L2 caches and only share the $12\text{ MB}$ Last Level Cache (L3). A highly contentious workload was generated by restricting the dataset to only $10$ keys (`--key-maximum=10`), forcing threads to repeatedly access and modify the same memory addresses.

### Environment Setup & Commands

#### 1. Base Scenario (Isolated Execution)

Run Memcached on only one logical core:

```bash

#!/bin/bash

MEMCACHED_CORES="1"
CLIENT_CORES="6"
PORT="11211"
DURATION="40"

trap 'echo "Cleaning up..."; kill $MEMCACHED_PID 2>/dev/null' EXIT

echo "Starting memcached on cores $MEMCACHED_CORES..."
taskset -c $MEMCACHED_CORES memcached -u nobody -m 512 -t 2 -l 127.0.0.1 -p $PORT &
MEMCACHED_PID=$!

sleep 3


if ! ss -lntp | grep -q $PORT; then
  echo "Error: memcached failed to start!"
  exit 1

  -e cpu_core/cycles/uP,cpu_core/instructions/uP,cpu_core/cache-misses/uP,cpu_core/cache-references/uP \
```

> [!IMPORTANT]  
> **Symptom Diagnostics:**
> *   **Snoop Interventions (HITM Explosion):** The most critical indicator of cache thrashing is the `mem_load_l3_hit_retired.xsnp_hitm` (Hit In Modified) counter. In the isolated Base Scenario, this value was negligible ($58,803$). However, in the dual-core setup, it exploded to over $19\text{ million}$ ($19,094,737$). This indicates that Cores $1$ and $3$ are constantly requesting cache lines that have been modified by the other core, forcing costly L3 cross-snoops and invalidations.
> *   **Cache Activity & CPU Cycles:** As a direct result of this bouncing cache line phenomenon (True/False sharing), total cache references nearly doubled from $\sim 34.5\text{ million}$ to $\sim 66.1\text{ million}$. Consequently, the CPU had to spend significantly more cycles ($8.1\text{ billion}$ vs. $6.6\text{ billion}$) to execute roughly the same number of instructions, demonstrating severe pipeline stalls due to memory access latency.
>
> This experiment conclusively proves that the lock contention and False Sharing previously identified via `perf c2c` drastically degrade performance when threads are scheduled across cores that do not share lower-level caches.

### `perf record` Analysis
*System-wide memory loads and local network overhead bottlenecks.*

<p align="center">
  <img src="images/record2.png" alt="perf record output" width="85%">
</p>

#### Objective
To analyze the memory load profiling data generated by `perf record` during the memcached benchmarking session to identify system bottlenecks.

#### Methodology
Profiling was conducted using the Linux `perf` tool, specifically targeting the `cpu_core/mem-loads-aux/` event to sample memory read operations on the Performance Cores (P-Cores). The benchmark was executed using `memtier_benchmark`.

#### Observations
The `perf report` output (based on approx. $24\text{K}$ samples) reveals a significant skew in processing overhead toward the Linux kernel’s network stack rather than the memcached application logic:
*   **Kernel Network Overhead:** The top functions contributing to memory load overhead are exclusively kernel-space TCP/IP routing and socket management functions. Notably, `tcp_wfree` accounts for $20.48\%$, followed by `__ip_local_out` ($17.13\%$) and `ip_send_check` ($10.49\%$).
*   **Application Logic:** User-space memcached functions represent a minor fraction of the sampled events. Functions such as `complete_nread_ascii` and `item_remove` account for only $2.41\%$ and $1.51\%$ respectively.
*   **Synchronization Primitives:** Minor overhead is observed in locking mechanisms, such as `native_queued_spin_lock_slowpath` ($0.54\%$) and `pthread_mutex_lock` ($0.50\%$).

> [!WARNING]  
> **Loopback Bottleneck:** The overwhelming dominance of network stack operations indicates a severe loopback bottleneck. Because both the load generator (`memtier_benchmark`) and the target server (`memcached`) run on the exact same host (`localhost`), the CPU spends the majority of its time processing high-throughput local network packets rather than executing database operations. While False Sharing and Cache contention (HITM) are underlying architectural issues within memcached, their visibility in general memory load profiling is currently obscured by this localhost network overhead.

#### Objective
To analyze the `perf c2c` (Cache-to-Cache) profiling results to pinpoint the exact memory addresses and source code lines responsible for the high HITM (Hit In Modified) rates observed in the memcached benchmark.

#### Methodology
The `perf c2c` tool was used to track shared data cache line contention. We examined the "Shared Data Cache Line Table" and drilled down into the most heavily contended cache line. The offsets within this cache line were mapped directly to the memcached source code using DWARF debug symbols.

#### Observations
*   **Top Contended Cache Line:** The `perf c2c` summary table identifies cache line `$0x5ef6379a5600$` as the primary bottleneck, recording the highest number of HITMs (Hit In Modified).
*   **Offset Analysis (The Smoking Gun):** Inspecting the details of cache line `$0x5ef6379a5600$` reveals two distinct memory offsets being accessed concurrently by different functions:
*   **Offset `$0x28$`:** Accessed by the `get_cas_id` function at `items.c:106`. The source code shows this is a write/increment operation on a shared counter (`++cas_id;`).
*   **Offset `$0x38$`:** Accessed by the `assoc_find` function at `assoc.c:75`. The source code shows this is a read operation checking hash table expansion states (likely reading `expand_bucket` or `hashpower`).
*   **Proximity:** The physical distance between these two variables in memory is only $16\text{ bytes}$ ($0x38 - 0x28 = 0x10$).


> [!TIP] 
> ### 💡 Diagnostic: False Sharing
> A standard CPU cache line is $64\text{ bytes}$. Because the heavily written `cas_id` variable (offset `$0x28$`) and the heavily read hash table state variables (offset `$0x38$`) are packed into the same $64\text{ -byte}$ cache line, they share the same cache coherency state.
> 
> Every time a CPU core allocates a new item and increments `cas_id`, it modifies the cache line, forcing the CPU to invalidate this line across all other cores. When another core attempts to simply read the hash table state via `assoc_find`, it suffers a costly LLC (Last Level Cache) miss and a HITM penalty, as it must fetch the dirtied cache line from the modifying core.

## Working Set Size (WSS) Experiment

### Objective
To evaluate the impact of scaling the **Working Set Size (WSS)** on the CPU cache hierarchy (L1d, L2, LLC) and overall execution efficiency in a Memcached environment. By controlling the number of active database keys, we analyze how memory access bottlenecks shift from CPU execution-bound states to latency-bound main memory fetches.

---

### Methodology
The experiment isolates memory access behaviors across different cache domains by scaling the number of active keys in the working set. The sizing targets specific boundaries of the hybrid Intel P-core architecture ($48\text{ KB}$ L1d, $1.25\text{ MB}$ L2, and $12\text{ MB}$ shared L3 LLC):

*   **Base Scenario ($<20\text{ KiB}$):** Highly localized execution environment.
*   **L1 Target ($\sim 20\text{ KiB}$ / $150$ keys):** Fits comfortably inside the $48\text{ KB}$ L1 Data Cache.
*   **L2 Target ($\sim 1\text{ MiB}$ / $7,000$ keys):** Exceeds L1d capacity but fits entirely inside the $1.25\text{ MB}$ L2 Cache.
*   **LLC Target ($\sim 8\text{ MiB}$ / $55,000$ keys):** Exceeds L2 capacity but fits inside the $12\text{ MB}$ Last Level Cache (L3).

For each scenario, Memcached was populated, and $100,000$ pipeline-optimized `GET` requests were executed using `memtier_benchmark`. Performance metrics were gathered using `perf stat` and hardware events were analyzed through kernel-level calls.

---

### Execution Scenarios & Profiling

#### 1. Base Scenario ($< 20\text{ KiB}$)
Establish a baseline workload with negligible memory pressure.

```bash
#!/bin/bash

MEMCACHED_PORT=11211
CPU_CORE=2
L1_ITEMS=150         
GET_REQUESTS=50000    
DATA_SIZE=64

echo ">>> 1. Restarting Memcached and Pinning to CPU $CPU_CORE..."
pkill memcached
sleep 1

taskset -c $CPU_CORE memcached -u nobody -p $MEMCACHED_PORT -m 64 -l 127.0.0.1 &
MEMCACHED_PID=$!

echo "Memcached started with PID: $MEMCACHED_PID on CPU $CPU_CORE"

echo "------------------------------------------------------"
echo ">>> 2. Phase 1: SET (Filling L1 Cache)..."
taskset -c 6 memtier_benchmark -s 127.0.0.1 -p $MEMCACHED_PORT -P memcache_binary \
  --ratio=1:0 -n $L1_ITEMS -c 1 -t 1 -d $DATA_SIZE \
  --key-pattern=S:S --key-maximum=$L1_ITEMS

echo "------------------------------------------------------"
echo ">>> 3. Phase 2: GET (Measuring L1 Baseline)..."

sudo perf stat -p $MEMCACHED_PID \
  -e cpu_core/L1-dcache-loads/uP,cpu_core/L1-dcache-load-misses/uP,cpu_core/l2_rqsts.miss/uP,cpu_core/l2_rqsts.references/uP \

  --ratio=0:1 -n $GET_REQUESTS -c 1 -t 1 \

sudo perf stat -p $MEMCACHED_PID \
  -e cpu_core/LLC-loads/uP,cpu_core/LLC-load-misses/uP \
  memtier_benchmark -s 127.0.0.1 -p $MEMCACHED_PORT -P memcache_binary \
  --ratio=0:1 -n $GET_REQUESTS -c 1 -t 1 \
  --key-pattern=S:R --key-maximum=$L1_ITEMS  

sudo perf stat -p $MEMCACHED_PID \
  -e cpu_core/LLC-stores/uP,cpu_core/LLC-store-misses/uP \
  memtier_benchmark -s 127.0.0.1 -p $MEMCACHED_PORT -P memcache_binary \
  --ratio=0:1 -n $GET_REQUESTS -c 1 -t 1 \
  --key-pattern=S:R --key-maximum=$L1_ITEMS


sudo perf stat -p $MEMCACHED_PID \
  -e cpu_core/cache-misses/uP,cpu_core/cache-references/uP,cpu_core/cycles/uP,cpu_core/instructions/uP \
  memtier_benchmark -s 127.0.0.1 -p $MEMCACHED_PORT -P memcache_binary \
  --ratio=0:1 -n $GET_REQUESTS -c 1 -t 1 \

echo ">>> Base Scenario Completed"
```

### Detailed Architectural Analysis

#### Instruction vs. Cycle Cost (CPI Degradation)
To understand execution efficiency, we compute the average **Cycles Per Instruction (CPI)** across the scenarios:

$$\text{CPI} = \frac{\text{Cycles}}{\text{Instructions}}$$

*   **Base Scenario:** $\text{CPI} = \frac{139.6\text{M}}{231.7\text{M}} \approx \mathbf{0.60}$
*   **L1 Scenario:** $\text{CPI} = \frac{254.1\text{M}}{359.1\text{M}} \approx \mathbf{0.71}$
*   **L2 Scenario:** $\text{CPI} = \frac{300.5\text{M}}{367.9\text{M}} \approx \mathbf{0.82}$
*   **LLC Scenario:** $\text{CPI} = \frac{353.6\text{M}}{371.7\text{M}} \approx \mathbf{0.95}$

While the overall instruction count remains highly stable once the application is loaded (ranging between $359\text{M}$ and $371\text{M}$ total instructions), the executed cycles increase significantly from $254\text{M}$ to $353\text{M}$ ($+39.1\%$). This represents a major CPI degradation of **$+58.3\%$** from the Base baseline, showing that the CPU spend more time stalling while waiting to fetch data from memory.

#### L2 Cache Saturation Dynamics
When transitioning from the L1 scenario to the L2 scenario:
*   **`l2_rqsts.miss`** scales from $207,340$ up to $1,910,847$ (an increase of **$+821.6\%$**).
*   **`LLC-loads`** spikes from $14,299$ to $280,147$ (an increase of **$+1,859.2\%$**).

This confirms that the active lookup keys have saturated L1, pushing requests down to the L2 and LLC cache layers.

#### LLC Stress and DRAM Fallback
When scaling the workload to the $55,000$-key LLC configuration:
*   **`cache-misses`** reach $1,778,120$, representing a $5\text{x}$ increase compared to the L2 configuration ($357,620$).
*   **`LLC-load-misses`** peak at $159,984$, with **`LLC-store-misses`** climbing to $39,462$.

Because the active dataset spans across the boundaries of the $12\text{ MB}$ L3 cache, standard L3 evictions begin to occur. Consequently, these evictions trigger direct, un-cached read loops to system RAM, which is the primary cause of the cycle inflation to $353.5\text{M}$ cycles.

### Core Finding
As the Working Set Size (WSS) scales through the hardware cache hierarchy, the primary performance bottleneck transitions from a **compute/scheduling-bound** profile (allocating slabs and managing events) to a **latency-bound** profile. At larger scales, Memcached performance is primarily determined by pointer chasing during hash table lookups (`assoc_find`), where random memory accesses bypass prefetching logic and trigger costly trips to main RAM.
